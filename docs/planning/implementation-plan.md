# IssueDigest 구현 계획

상태: 검토안 · 2026-10-11 한국 시간. 이 문서는 구현 완료 보고가 아니다.

## 목표와 합의

DigestWorks/IssueDigest를 새 서비스의 모노레포로 사용한다. 첫 사용자는 우리 둘이다. 하나의 이슈를 조사하면서 자료를 모으고, 주장을 비교하고, 근거를 확인하고, 후속 질문과 변화 확인에 재사용하는 작업 공간을 만든다.

서비스명은 IssueDigest다. 기존 LawDigest의 피드·프론트·단순 API는 가져오지 않는다. 수집·정제 규칙과 데이터·원문·식별자·이력은 검증 후 재사용한다. React Router, Python/FastAPI, Neo4j 및 PostgreSQL·pgvector·PydanticAI/DBOS(D011)를 결정했다. PoC와 프로덕션은 동일한 데이터 계약·엔진·실행 경로를 사용하며, 첫 배포에서는 자료량·사용자·지원 도구를 줄인다.

서버·DB·저장소·AI API를 포함한 월 운영비 상한은 10만 원이다. 개발 서버의 사용자 전용 환경·웹/API 실행은 승인 범위에서 검증했다. 기존 백엔드·AI 파이프라인과의 관계·실제 데이터·운영 자원 배정·비용은 추가 확인하며 운영 DB를 변경하지 않는다.

Sites는 현재 결정·진행·판단 요소·이력의 공유 화면이다. 구현 계획·요구사항·판단 근거는 이 저장소에서 버전 관리하고 Sites에 같은 상태로 반영한다. 아직 자동 동기화나 공동 편집 기능을 구현한 것은 아니다.

운영 데이터의 건수·기간·최근 성공 시각과 서버 사양은 확인하지 않았다. 코드 존재를 현재 수집 성공으로 표현하지 않는다.

## 첫 사용자 여정

1. 초대된 두 사용자가 같은 작업 공간에서 이슈를 만든다.
2. 허용된 출처의 URL·문서·API 자료를 등록하고 수집·파싱·연결 상태를 확인한다.
3. 질문에 사용할 원자료와 기간을 선택해 조사 질문을 보낸다.
4. 접수·검색·도구 실행·검증·화면 구성 상태를 보고, 준비된 결과부터 읽는다.
5. 비교표·타임라인·관계도·차트·근거 카드에서 원문 위치와 데이터 시점을 확인한다.
6. 후속 질문은 현재 선택과 화면을 이어받아 관련 부분만 갱신한다.
7. 질문·자료 버전·결과를 저장하고 동료가 같은 결과를 다시 열어 후속 조사를 한다.
8. 수집된 새 버전과 이전 결과를 비교한다. 변경 확인이 이전의 저장 결과를 덮어쓰지 않는다.

공동 작업의 첫 범위는 같은 이슈·자료·질문·결과를 저장·열람하는 것이다. 실시간 동시 편집·커서·댓글·알림은 첫 완료 조건에서 제외한다. 동시 변경 충돌은 버전 확인으로 처리한다.

## 첫 범위 제안

- 대표 이슈 1개, 관련 실제 원자료 30~50건, 평가 질문 20개. 이는 제안 수치다. 주제는 원문·관계를 확보할 수 있는 이슈로 함께 고른다.
- 우선 자료: 기존 법안·상태·주체, 관련 법령·심사자료 또는 정부 발표. 통계·뉴스·청원·여론조사는 선택 이슈에 필요한 자료만 연결한다.
- UI 요소: 근거 카드, 비교표, 타임라인, 관계도, 실제 수치 차트. 처음부터 고정 탭을 결과로 채우지 않고 질문별 화면 명세를 생성한다.
- 조회 도구: 기존 데이터 검색, 관계 조회, 검증한 공급처별 API/MCP. 웹 수집은 API로 확보하지 못한 허용 원문에 한정한다.
- 이미지 검색·생성·크롭·리사이즈는 같은 실행·저장·비용 체계 안의 후속 도구로 구현한다. 생성 이미지는 설명용이며 실제 사건·통계의 근거가 아니다.
- 첫 버전도 인증·공유 저장·취소·재접속·실패 복구·백업·사용량 관리를 포함한다. 공개 회원가입, 전면 수집, 과금·구독, 일반 웹 코드 실행은 범위 밖이다.

## 구조 제안과 확정할 경계

| 영역 | 제안 | 결정 상태·검증 |
| --- | --- | --- |
| 웹 | React Router + React + TypeScript | 프레임워크 결정. 렌더링 모드는 앱의 접근·공유 요구로 선택 |
| API·도메인 | Python + FastAPI + Pydantic, API와 워커가 도메인 공유 | 언어·프레임워크 결정. 계약·버전은 첫 작업에서 고정 |
| 기준 데이터 | PostgreSQL + SQLAlchemy + Alembic | D011 확정. 기존 MySQL은 이관 입력 후보. 불변 원문/인용 저장부터 구현 |
| 검색 | PostgreSQL + pgvector + 이름/번호·한국어 어휘 검색 조합 | D011 확정. 한국어 어휘·정확 ID·필터 품질은 실제 평가셋으로 검증 |
| 그래프 | Neo4j, 기준 데이터에서 투영 | 엔진 결정. 원문·시점·관계 근거를 포함하고 동기화·재구축 검증 |
| 에이전트 | PydanticAI + 하나의 조율 에이전트·등록된 도구 | PydanticAI는 D011 확정. 조율 방식·도구 범위는 검증. Decisions는 고정 선택 판단, Responses는 설명·UI 명세 생성 |
| 작업 복구 | PydanticAI + DBOS/PostgreSQL | D011 확정. 중단·버전 변경·재시도·스트리밍 품질은 후속 검증 |
| 원문·이미지 | S3 호환 저장소 + 원문 위치·해시·버전 | 기존 저장소·보관량·외부 백업 가능 여부를 확인 후 제공자 결정 |
| 인증 | 관리형 OIDC + FastAPI 세션 + 초대 사용자 허용 목록 | 공급자 미정. 작업 공간 권한은 서버에서 확인 |
| 운영 | Docker로 웹·API·워커·DB를 구분, 기존 서버 우선 검토 | 서버 사양·공존 자원·백업 확인 후 배치 결정. 초기 목표는 단일 서버 운영 |
| 추적·평가 | OpenTelemetry, 저장된 실행 이벤트·사용량, pytest/Playwright | Langfuse 등 추가 서비스는 비용·자원 확인 후 선택 |

이것은 기능과 완료 기준을 유지한 생산 목표 구조 제안이다. 예산이 작다는 이유로 가상 데이터·메모리 저장·복구 없는 임시 앱으로 대체하지 않는다. 기존의 관리형 ECS/RDS/OpenSearch/Temporal 중심 추천은 새 예산·기존 서버 정보에 맞춰 재평가한다. 단일 서버는 장애 시 중단될 수 있어 백업 복구가 필요하며, 고가용성을 약속하지 않는다.

검증 기준과 비교 근거는 [결정 기록](decisions.md), 화면·도구·저장 계약은 [요구사항·설계](requirements-design.md)에 둔다.

### 제안 모노레포 배치

```text
apps/web/                 React Router 앱
apps/api/                 FastAPI, 세션·권한·실행 API
apps/worker/              수집·투영·에이전트 실행
packages/domain/          문서·주장·관계·검색 계약과 규칙
packages/connectors/      기존 수집 자산을 감싼 공급처별 도구
packages/agents/          조율·검증·화면 명세
packages/ui/              허용된 컴포넌트·액션·명세
infra/                    Docker·배포·백업·운영 설정
tests/evaluation/         실제 자료·질문·기대 근거·평가 결과
docs/planning/            계획·요구사항·결정·진행·기록
```

초기 계획 단계에서는 문서만 생성했다. 이후 [개발 실행 기반](../changes/development-foundation.md)에서 웹·API·상태 계약·개발 검증을 구현했다. 워커·엔진·제품 기능은 별도 작업이며 클라우드 자원이나 운영 배포는 생성하지 않았다.

## 단계별 작업과 완료 조건

| 단계 | 작업 | 완료 조건 | 선행 조건 |
| --- | --- | --- | --- |
| P0 · 계획 | 기존 자산·결정·와이어프레임 정리, 첫 범위·계약·과제 작성 | 계획 문서와 Sites에 동일 상태 표시, 검토 가능한 PR | 이번 요청 |
| P1 · 기반 | 웹/API/워커, 계약·권한·마이그레이션·CI·개발 환경 | 두 사용자 권한, 계약 타입, 동일 엔진 기동·테스트, 요청 ID 추적 | 기준 DB·인증·실행기 결정 |
| P2 · 실제 근거 | 원천 스냅샷, 1~2개 연결기, 원문·버전·인용 위치, 증분·재처리 | 동일 자료 재수집 시 중복 없음, 변경 버전 보존, 실패 원인 확인 | 첫 이슈·자료 접근·보관 조건 |
| P3 · 검색·관계 | 평가셋, 한국어 검색·벡터·재순위화, Neo4j 투영 | 기대 근거 검색, 근거 있는 경로, 삭제/정정·버전 반영, 재구축 | 실제 자료·기준 DB |
| P4 · 탐색 화면 | 조율·Decisions·도구·Responses·검증·스트리밍·부분 갱신 | 질문별 결과 생성, 원문 연결, 불충분 안내, 취소·재접속·복구 | 검색·실행기·허용 UI 계약 |
| P5 · 공유·시각 도구 | 질문·결과 버전 저장·재열람, 이미지 검색·생성·편집 | 두 사용자가 같은 결과 확인, 이미지 출처·이력·용도 표시, 새 자료와 비교 | 권한·결과 저장·이미지 공급자 |
| P6 · 운영 검증 | 운영 배치·백업 복원·지출 한도·장애·사용자 평가 | 같은 실제 과제의 정확성·시간·비용·복구 결과로 출시 판정 | 서버 상세·배포 권한·예산 측정 |

P4 이전에는 P2의 실제 자료로 검색·인용을 검증한다. 이미지 표현보다 근거·저장·복구 경로를 먼저 완성한다. 단계는 작업 순서이며 별도 PoC 스택으로 전환하는 일정이 아니다. 시간 추정은 서버·자료·도구의 접근 확인 뒤 작업별로 산정한다.

## 품질과 예산

첫 평가의 제안 기준: 대표 질문에서 핵심 인용 정확도 95% 이상, 중대한 주체·법안·상태 오연결 0건, 정보 부족 질문에 근거 없는 답변 0건. 일반 검색과 비교해 조사 시간을 30% 줄이면서 정확성을 유지하는지 두 사용자의 같은 과제로 확인한다. 소수 표본의 결과를 전체 서비스 성능으로 일반화하지 않는다.

두 동시 사용자 환경에서 접수 상태 1초 이내 표시를 목표로 하고, 첫 유용한 결과·전체 완료의 p50/p95와 실패율을 측정한다. 검색·이미지·모델 지연을 나눠 확인하며 전체 완료 시간은 측정 후 목표를 정한다. 새로고침 후 진행 작업 재연결, 마지막 정상 결과 보존, 실패 작업 재개, 백업 복원까지 통과해야 한다.

아래는 청구 견적이 아니라 월 상한을 위한 예산 배분 제안이다. 서버 견적·기존 자원·자료량·실제 API 사용량을 확인해야 한다.

| 항목 | 배분 상한 제안 |
| --- | ---: |
| 서버·DB 운영 | 60,000원 |
| 모델·임베딩·검색·이미지 API | 20,000원 |
| 원문 저장·외부 백업 | 10,000원 |
| 세금·환율·전송 등 예비분 | 10,000원 |
| 합계 | 100,000원 |

기존 서버의 분담 비용도 합계에 포함한다. 요청 전 최대 토큰·도구 사용량에 대한 비용을 예약하고, 완료 시 실제 사용량으로 정산한다. 월 한도·동시 실행·도구별 한도를 서버에서 적용한다. 한도에 도달하면 기존 자료 열람은 유지하고 새 유료 실행을 중단한다. 캐시·저장 결과 재열람·필터에는 모델을 호출하지 않는다. 공급자 예산 알림을 강제 차단으로 가정하지 않으며, 외부에서 같은 키를 사용하는 비용은 별도 집계한다.

## 사용자 준비 사항

1. 첫 이슈와 실제로 해결할 조사 질문 3~5개를 선택한다. 후보는 자료 확보가 가능한 청년 주거·교통, 돌봄·노동 등이며 아직 확정하지 않았다.
2. 개발 서버 접속·기초 사양은 확인했다. 전용 가용 자원·월 분담 비용·기존 수집 서버와의 관계, 데이터 실행 커밋·수집 상태·원문 위치는 후속 확인한다. 운영 데이터는 우선 읽기 스냅샷으로 가져온다.
3. 동료의 GitHub 협업 접근과 앱에 사용할 로그인 계정을 준비한다. 초대 메시지는 사용자가 보낸다.
4. 구현 환경이 정해지면 프로젝트별 모델·데이터 API 키와 승인 상태를 그 환경의 비밀 설정에 등록한다. 대화·공개 저장소·Sites에 키를 넣지 않는다.
5. D011의 저장·검색·실행 엔진을 구현하고 검증한다. 인증·배포안을 결정한다. 서버를 기다리는 동안 계약·기존 자산 평가·자료 선정·개발 환경 계획은 진행할 수 있다.
