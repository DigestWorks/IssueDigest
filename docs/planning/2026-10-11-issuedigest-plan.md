## 개요

IssueDigest는 기존 서비스 모두의입법(LawDigest, lawdigest.kr, 자연어 처리 기반 법률 개정안 요약 플랫폼)을 다시 설계해 만드는 새 프로덕트다. 기존 서비스는 법안 요약을 피드 형태로 제공했다. 새 프로덕트는 뉴스·여론조사·청원·법안 등 여러 자료를 연결해 이슈의 맥락, 근거, 변화를 제공한다(검토 페이지 「현재 방향」).

민재와 재신 두 사람이 진행한다. 포트폴리오용이 아니라 두 사람이 실제로 해 보고 싶은 기술과 제품에 집중하기로 했다(대화, 10월 7일 이전).

## 확정 사항

대화와 검토 페이지에서 두 사람이 합의했거나 결정으로 표시된 내용이다.

### 제품

- 기존 피드형 서비스를 버리고 제품을 재설계한다.
- 기존 데이터와 핵심 수집·가공 흐름은 재사용한다.
- 뉴스·여론조사·청원·법안 등을 의미 있는 정보로 연결한다.
- 프로덕트 이름은 IssueDigest로 한다. 민재가 제안했고 재신이 동의했다. 서비스 범위는 미결이다.

### 진행 방식

- 민재와 재신 두 사람이 진행한다.
- PoC와 프로덕션은 같은 기술 스택과 구조를 사용한다.
- PoC 작업은 10월 10~11일 주말에 시작하고, 제품 방향은 그 전에 정한다(10월 8일 합의).

### 기술 스택 (검토 페이지에서 「결정」으로 표시된 항목)

| 영역 | 결정 |
| --- | --- |
| 프론트엔드 | React Router, React, TypeScript |
| 백엔드 | Python, FastAPI. API와 수집·처리 워커가 도메인 코드를 공유한다 |
| 그래프·온톨로지 저장소 | Neo4j |

### 이미지 에셋

- 이미지 에셋은 검색으로 먼저 확보하고, 검색으로 구할 수 없는 경우에만 생성한다. 생성은 비용이 들기 때문이다(민재 제안, 재신 동의).
- 이미지 생성에는 비용이 가장 낮은 모델을 사용한다(재신 의견).

## 제안 사항

한쪽이 제안했고 결정 전인 내용이다.

### 민재

- 수집한 뉴스·여론조사·청원·법안 데이터를 기반으로 내부 온톨로지를 확장한다.
- 온톨로지를 기반으로 그래프 RAG를 구성해 사용자에게 보여 줄 이슈 데이터를 가져오고, generative UI로 화면을 구성한다.
- 「Jev」를 비용 최적화와 시맨틱 라우팅에 적극적으로 사용한다(아래 「확인 필요 항목」).
- 사용자 요구는 단순 질의응답부터 시각화된 디자인 리포트 생성까지 대응한다.
- 양질의 디자인 컴포넌트를 미리 많이 마련한다. 차트와 다이어그램은 shadcn 컴포넌트를 활용한다.
- 공공 AX 프로젝트에서 공개된 MCP 서버를 데이터 수집에 적극 활용한다.
- 데이터 수집처를 늘리는 것보다 내부 온톨로지를 얼마나 잘 구축하고 활용하는지가 더 중요하다.

### 재신

- 온톨로지, RAG, 에이전트 시스템 경험을 쌓고 싶다. 에이전트 시스템은 내부 데이터 처리에 활용한다.
- 디자인 패턴을 스킬처럼 문서화하고, 질문이 들어오면 Decisions API로 어떤 디자인을 쓸지 결정한다. 이 방식이면 「luna」 같은 모델로도 대응할 수 있다고 봤다.
- 이미지 생성과 크롭을 포함한 작업 흐름을 에이전트로 구성할 수 있다. 「agents api」는 비용이 커서 비교용으로 내부에서만 써 볼 수 있다.
- 검토 페이지의 기술 스택 유력안(아래 「기술 스택 비교안」).

### 데모 (재신, 10월 8일)

- 더미 데이터로 주제 3개를 넣었다.
- Decisions API가 사용자 질문에 대해 표현 방식, 화면 배치, 자료 범위, 답변 가능 여부를 정한다.
- Responses API가 구체적인 답변을 생성한다.
- 모델은 gpt-5.4-mini를 사용했다.

## PoC 최소 품질 기준 (초안)

검토 페이지의 초안을 그대로 옮겼다. 수치는 제안값이며, 같은 평가 과제로 일반 검색·기본 RAG와 비교한 실제 측정 결과로 조정한다.

### 기술 품질

- 검증 가능한 답변: 핵심 주장마다 원문, 인용 위치, 시점을 제공한다. 평가셋 인용 정확도 95% 이상, 주체·법안·상태의 중대한 오연결 0건.
- 불확실성 표시: 근거가 부족하면 답변을 유보하고, 상충 자료와 모델 추론을 명시한다.
- 재처리·복구: 실패한 작업을 중복 적재 없이 재개한다. 원문 버전과 검색·그래프의 갱신 상태를 확인할 수 있다.
- 실행 상태 확인: 진행·완료·실패가 화면에 표시되고, 새로고침 후에도 작업과 결과를 다시 확인할 수 있다.

### 상품 품질

- 한 과제 완료: 사용자가 배경·주체·쟁점·현재 상태를 이해하고 필요한 근거를 찾는 과정을 도움 없이 끝낸다.
- 조사 시간 단축: 같은 과제를 일반 검색으로 수행할 때보다 시간을 30% 이상 줄이고 정확성을 유지한다.
- 근거 확인: 답변에서 원문으로 바로 이동하고, 어떤 자료가 어떤 주장을 뒷받침하는지 확인할 수 있다.
- 재사용 이유: 후속 질문이나 변경 확인 과제에서도 유용하다. 사용자 평가에서 반복 이용할 구체적 이유를 확인한다.

## 미결 사항

- 서비스 범위: 입법 중심으로 넓힐지, 정치·시사 전반을 대상으로 할지. 재신의 10월 10일 질문에 대한 답이 필요하다.
- 첫 사용자와 해결할 과제, PoC에서 다룰 첫 이슈 주제
- 서비스 형태, 반복 이용 이유, 지불 이유
- 온톨로지·그래프·RAG·에이전트·UI의 조합. 민재가 제안한 「온톨로지 → 그래프 RAG → generative UI」 구성을 채택할지
- 기술 스택 비교안의 각 항목
- 역할 분담. 10월 7일 회의에서 역할을 나누기로 했고, 분담 결과는 대화에 기록이 없다.

## 결정 요청과 권고안

PoC를 시작하기로 한 주말이 이번 주말이므로 아래 항목을 먼저 정해야 한다. 권고안은 이 정리 과정에서 작성한 초안이며 두 사람의 합의 전이다.

1. 서비스 범위
   - 권고: 정치·시사 이슈 전반을 서비스 대상으로 하고, 법안·발의·이력·표결 데이터를 주된 근거 자료로 사용한다.
   - 이유: IssueDigest라는 이름을 제안한 이유가 입법보다 넓은 범위였다. 동시에 검토 페이지 기준으로 가장 잘 갖춰진 기존 데이터가 법안 관계 데이터다.
2. 첫 서비스 후보
   - 권고: 이슈 탐색.
   - 이유: 검토 페이지의 첫 검증 후보이고, 주장·근거 비교와 변화 추적이 같은 공통 코어를 사용하므로 이후 확장할 수 있다. 민재가 제안한 온톨로지 → 그래프 RAG → generative UI 구성을 가장 직접 검증할 수 있다.
3. PoC 첫 이슈 주제
   - 권고: 법안, 국회 회의록, 여론조사, 뉴스가 모두 존재하는 이슈 하나를 고른다.
   - 이유: 서로 다른 자료 사이의 연결이 온톨로지와 그래프 RAG의 효과를 확인하는 조건이다. 데모의 더미 주제 3개 중 이 조건을 만족하는 것이 있으면 그것을 쓴다.
4. 기준 데이터베이스
   - 권고: PostgreSQL. 검토 페이지의 추천안과 같다.
   - 이유: PoC와 프로덕션이 같은 스택을 쓰기로 했으므로 PoC 시작 전에 정해야 한다.
