# 최종 생성의 답변·부족 분기 규격

2026-10-28 KST. 실제 최종 v2 응답은 요약/비교를 만들었으나 `outcome=answer`와 내용이 있는 `message`를 함께 반환했다. 기존 canonical 계약은 답변의 message=null만 허용한다. 공급자에 전달한 JSON Schema에는 이 조건이 나타나지 않아, 스키마를 따른 응답도 서버의 후속 검증에서 실패했다. 응답과 실패 SQL은 그대로 보존하며 안내 문구를 삭제해 성공으로 재분류하지 않는다.

## 변경

- 새로운 model-facing 입력 `question-briefing-source-v3`와 공급자 출력 도구 `compose_question_briefing_v2`만 추가한다. 최종 저장/앱 출력은 기존 generation-v1·QuestionBriefing 계약이다. v1/v2 프롬프트·지시·공급자 출력 도구 bytes와 결과 읽기는 유지한다.
- 새 도구는 `result` 안에서 답변과 부족 두 스키마 중 하나만 받는다. 답변 분기는 answer+modules만 허용하여 message 필드 자체를 금지한다. 부족 분기는 insufficient_evidence+message만 허용하여 modules 필드가 없다. 각 분기는 추가 필드를 거부한다.
- 서버는 답변에 message=null, 부족에 modules=빈 배열을 명시적으로 구성해 기존 canonical 검증을 수행한다. 모델이 낸 내용을 삭제하거나 수리하는 것이 아니다. 첫 summary·참조·날짜·의존성 등 기존 검증도 유지한다.
- v3 입력은 v2의 모든 원문/참조/명제를 유지한다. 각 자료에 중복된 원문 해시와 질문 해시만 제거하고 역변환 때 동일한 원문 해시·정확 질문의 UTF-8 해시로 복구한다. 불일치 해시는 거부한다. 사실·조건·숫자·시점·한계는 삭제하지 않는다.
- 저장된 지시/프롬프트 해시와 결과 input_format으로 버전을 결합한다. 기본 입력 v1은 그대로이며, 검증 후 개발 환경만 v3를 선택한다. 구버전 프로그램은 v3 결과를 읽지 못하므로 복귀할 때도 세 입력을 읽는 새 코드의 v1 쓰기 모드를 사용한다.

## 실제 검증 범위

기존 분석3건은 재사용한다. v2 최종1회의 완료 응답·알려진 사용량·실패를 보존하고, 출력 규격 수정 후 새 검증 요청에서 최종 생성1회만 별도 승인한다. 자동 모델 수리·분석 재호출·기존 실패 행 덮어쓰기는 없다. 이 과정의 실제 요청 수는 분석3·최종v2 1·최종v3 최대1이다. 각 호출의 사용량과 예약액을 구분한다.

기존 실패 도구의 보정 전까지 v2 결과는 실패로 남긴다. v3 전체 원문/명제 역변환·실제 전체20k 요청 예산·스키마 분기·기존 v1/v2 바이트·현재 권한/저장/재열람·전체 회귀와 독립 검토를 먼저 확인한다. 실제 최종 결과도 원문과 대조하는 AI 개발 검토이며 사람의 독립 사실 인증은 아니다.
