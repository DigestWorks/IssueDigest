# 생성 정체의 오프라인 비교 진단

2026-10-27. [직전 실제 실패](../research/question-scoped-runtime-validation.md)의 공백 정체를 기존 성공/실패 원응답과 비교한다. 이번 범위는 원인을 좁히는 진단·후속 설계 기록이며 새 생성 후보·제공자 호출·DB 변경·서비스 전환이 아니다.

## 고정 조건

기존 생성 SDK/지침/schema·공백256/시간/예산·원문/질문·과거 실행 상태/usage를 바꾸지 않는다. 이전 아카이브를 읽기 전용으로 사용하고 새 private 분석/검사 결과만 별도 보존한다. 부분 JSON을 보완해 성공 출력으로 만들거나 부분 내용의 의미 점수를 매기지 않는다. 실패 단계와 제공자의 관측하지 못한 최종 상태를 구분한다. 사용량 미관측은0비용이 아니다.

## 확인할 질문

1. 실패 응답의 공백은 문자열 내부인가, 외부인가? 현재 guard로 어느 지점에서 재현되는가?
2. 마지막 비공백 값은 실제 송신 schema에서 허용되는가? 같은 schema의 완성 응답에 해당 구조의 유효 예가 있는가?
3. 원문/질문·tool schema·지침·version·호출 경로 중 무엇이 같고 무엇이 다른가? 성공/실패를 한 변수의 효과로 해석할 수 있는가?
4. 재현 가능한 관측과 제공자 내부 원인에 대한 미확인 가설은 무엇인가?

## 작업

- [x] 이전v3 실패·v4 완료·v5 실패의 SSE/인자·송신 schema를 읽기 전용 비교.
- [x] lexical 상태·이스케이프·문자열 내부 공백·불완전 stream 진단 검사를 실행.
- [ ] 독립 결과 검토·기록/PR/Sites 갱신·과거 아카이브/제품 bytes 보존.
- [x] 후속 생성 전략의 단일 변수 실험 원칙 정의. 후보 채택·실제 설계는 후속. 이번에는 실제 호출하지 않음.

## 판정 경계

완성된 유효 예가 있더라도 특정 응답의 공백 반복 원인은 증명되지 않는다. schema 크기/중첩·지침·모델·전송 형태의 책임을 임의로 단정하지 않는다. 근거 없는 버전 추가 대신 진단 후 생성 단계의 구조를 재검토하고, 새 유료 검증은 별도 동결/모의/검토·예산 조건으로 계획한다. 현재 앱·main/운영·Actions는 유지한다.
