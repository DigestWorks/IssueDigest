# 역할 경계·출력 배분 v2 · 실제 제한 평가

2026-10-22 한국 시간. 호출 전 사전 기준이다. [구현된 SDK](../changes/semantic-balanced-output-implementation.md)의 실행 코드·지침·동적 schema·한도를 고정하며, 기존446실행/설정/테스트·361실제 증거와 과거 gold/점수/실패 비용을 보존한다. 연구/문서 작업으로 앱/API/UI/DB/worker·기본 모델·서버/main을 변경하지 않는다. 새 전체QA7,808개는 실행 코드가 같아 재사용하며 새 제품 코드 구현/SDD 자원은 만들지 않는다.

## 자료·비교 경계

기존 G/H/I/J/K와 동일한 완전한 원문을 새 생성→새 검수로 평가한다. 새 검수는 concrete v2 생성만 받으므로 과거 generation을 형식 변환하거나 참조용 합성 usage를 실제 사용량으로 넣지 않는다. 전부 이미 본 개발 자료이며 독립 holdout/일반 정확도/중립성 검증이 아니다. 이전 G/H/I 검수는 과거 결과를 입력받았지만 이번 검수 입력은 새 생성이므로 순수한 동일 입력 검수 비교가 아니다.

## 사전 의미 기준

전체 필수 수치·단위·근사/열린 상한·상태·기간·조건/목적/비교 기준·명시 범위/기관·관계를 원문과 수동 대조한다. 새 결과/검수 경고를 보기 전에 구체 수치 catalog·필수 후보·기준과 원래 gold를 비공개 고정본에 보존한다.

- G: 필수 학교 수·현재/목표 지원 규모를 보존하고 날짜만 별도 실적 수치로 만들지 않는다. 중요한 프로그램 구성 한정어의 실제 손실과 대상 범위로의 분류를 구분한다. 목적의 수혜자를 배타적 집계 모집단으로 자동 확정하지 않고, 확실한 material entity 한정어 누락을 역할 분류 차이만으로 uncertain으로 낮추지 않는다. 목표 기간의 공동 적용이 불분명하면 단정하지 않는다. 과거 정상 gold/점수는 그대로 유지하며 독립 사람 재판정 전에는 G 전체의 새 정상 정확도 충족을 확정하지 않는다. 수치 보존·명확 누락·분쟁 부분은 따로 기록한다.
- H: 사업 수와 국비를 선택하고 사업 연도 및 적용되는 광역/세 하위 지역을 두 수치에 보존한다. 원래 누락을 그대로 만들어야 한다는 기준은 아니다. 새 생성에 실제로 남은 누락을 검수가 탐지하는지와 추가 hard 오탐을 평가한다.
- I: 필수 두 인원·첫 운영의 명시 기간과 실제 상태를 보존한다. 운영 주체를 집계 인원의 소속/필수 발표자로 만들지 않고, 인접한 목표에 기간·절대 연도를 추정해 넣지 않는다. 새 생성이 오류를 피했으면 과거 unsupported 진단 수를 강제하지 않는다.
- J: 원래 필수 신청/선정 수·지원액·국비 상한/지방비 하한, 두 수혜 지역·연간/지원 기간·상태를 보존한다. 재언급 수를 합산하지 않고 기간만 측정 사실로 만들거나 ‘각 지역당’/전체 합계를 추정하지 않는다.
- K: 필수 인원2·비중2·증감률2, 정당한 소속·전년도 비교 기준을 보존하고 두 증감률의 증가/감소를 명시 change로 연결한다. 인원·비중은 변화량으로 만들지 않으며 비교 기준을 절대 측정 연도로 바꾸지 않는다.

검수는 원래 생성이 선택한 각 수치와 다섯 역할의 실제 누락/근거 없는 추가/모호성을 판단한다. 원래 결과를 수정하지 않는다. 필수 수치 자체가 선택되지 않은 것은 생성 실패로 별도 기록하며 검수의 다섯 역할 coverage가 완전한 수치 선택을 인증한다고 해석하지 않는다. hard 탐지/미탐·추가 hard 오탐·uncertain·미완료를 분리한다. no_issues 상태나 검수의 오류 탐지가 생성 성공을 대신하지 않는다. G는 분쟁 사례로 전체5건 표와 시도 분모에 계속 남기고, 판정 가능한 비분쟁4건을 별도 표시할 때 제외 이유를 명시한다.

## 요청·실패·예산

G 생성/검수→H 생성/검수→I 생성/검수→J 생성/검수→K 생성/검수, 실패 포함 최대10요청·단계별1회이다. 생성 실패/빈 선택/검수 사전 용량 차단의 후속은 무호출로 남기고 다른 요청으로 대체하지 않는다. retry/repair/fallback0이며 미완료 JSON을 복구하거나 성공으로 재분류하지 않는다. 송신 가능하지만 사용량이 불명확한 실패가 생기면 남은 단계를 중단하고 비용을0으로 세지 않는다. 기존 소진 runner는 실행하지 않고 별도 실행 잠금·배타적 시도 기록을 사용한다.

[공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-6.1-sol)의 GPT-6.1 Sol/low·Responses·명시 default tier·30초/no-store다. 생성output1,800·검수min(1,100,2,500−실제 생성output), 생성/검수 합산total20,000/output2,500을 유지한다. 전체 원문·실제 raw/normalized schema·지침·framing2,048·출력reserve가 실제 잔여 안에 들어가야 한다. 후속 검수는 관측한 새 생성 결과/usage로 결정하고 실제 요청 전에 mock HTTP body/hash를 저장해 실제 송신과 일치하는지 확인한다.

[공식 standard 요율](https://developers.openai.com/api/docs/pricing)을 확인했다. 1M당 input$2/cached$0.10/30분write$2.50/output$10이며 input에 포함된 cached/write를 분리해 중복 계산하지 않는다. reasoning은 output에 포함한다. 과거 생성/검수 비용은 새 비용에서 제외하며 이번 실패 known usage는 포함한다. 참고 보수 상한은10요청×20,000을 모두 output으로 보아$2 이내이며, 실제 청구/환율은 미검증이다. 월10만 원 개발·운영 예산을 확대하지 않는다.
