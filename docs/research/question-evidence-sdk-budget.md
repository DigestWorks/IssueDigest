# 질문별 근거 명제 SDK · 무호출 예산 측정

2026-10-23 한국 시간. 기반 [순수 계약](../changes/question-evidence-propositions-implementation.md), PR99/89edac6. **요청 형식·지침 초안의 측정이며 제품 SDK 구현은 아니다.** 문서/비공개 무호출 시제품이므로 spec-driven-workflow 문서 예외를 적용한다. 기존464개 실행 파일과 원문/기준·모델 응답/점수/비용·이전 증거를 유지한다. 전체8,894QA를 재사용하고 새전체QA·서버/DB자원·앱/main 배포를 만들지 않는다.

## 측정 범위

기존6자료의 검증된 Source에서 모든 인용의 ID와 quote를 그대로 넣고 정확한 질문1개를 추가한 JSON 초안을 만들었다. 수치 catalog나 과거12명제 기준/정답을 provider 입력에 넣지 않았다. 질문은 일반 설계용1개를6자료에 사용하고, 가장 긴 개발 자료에는 원래4질문과 허용 최대 길이2,000자 합성 질문을 별도로 적용했다. 총11조건이며 원문/인용 순서·문자열이 전부 복원됨을 확인했다. 여러 인용/수치0인 Source 전체와 질문 최대 길이가 항상 수용된다는 일반 증명은 아니다.

출력 도구는 기존 `QuestionEvidenceInput` 전체8유형을 그대로 쓴다. 새 지침 초안은 출처 귀속·원문 지시 무시·수치/분배/경계/시간/자격/전제/부정/절차·unknown/uncertain·필수 빈/null 필드를 요구한다. 실제 생성 SDK의 최종 지침/형식/profile/hash는 아직 확정하지 않았다. 이 시제품에서 원래 citation ID를 쓴 것은 측정 조건이며 ID alias 형식 채택을 결정한 것도 아니다. 비공개 식별자/원문·질문·모의 전송 body는 공개 문서에 싣지 않는다.

## 입력 결과와 비교 기준

기존 helper와 설치된 SDK의 원래/정규화 도구 schema를 모두 측정했다. 도구 metadata를 포함한 raw8,955/normalized8,069 UTF-8 bytes 중 큰 값을 사용한다. SDK가 실제 모의 body에 붙인 기본 description까지 포함한 tools를 helper와 같은 JSON 직렬화 규칙으로 비교하면10건 모두8,114bytes로 helper normalized보다45bytes 컸다. 여전히 선택한 raw8,955bytes 이하여서 비교 값/차단 분류는 바뀌지 않는다. 지침1,182bytes·기존 framing 여유2,048·출력 예약1,800을 더한 **기존 방식의 보수적 비교 envelope**다. UTF-8 bytes와 출력 token 예약을 합한 사전 검사 값이며 실제 input token 수·제공자 context limit·요금이 아니다. 새 SDK 한도를 확정하거나 기존20,000/1,800을 바꾸지 않았다.

| 조건 | 비교 envelope | 기존20,000 대비 여유 | 모의 HTTP 요청 |
| --- | ---: | ---: | ---: |
| 작은5자료 + 일반 질문 | 14,458~15,302 | 4,698~5,542 | 각1 |
| 긴 개발 자료 + 일반 질문 | 17,374 | 2,626 | 1 |
| 같은 자료 + 원래4질문, 각 별도 | 17,374~17,400 | 2,600~2,626 | 각1 |
| 같은 자료 + 2,000자 합성 질문 | 23,264 | -3,264 | 0·사전 차단 |

원문을 자르거나 질문을 줄이지 않고 초과 조건을 그대로 남겼다. 순수 계약의 질문 상한2,000자는 개별 입력의 유효성 상한이며, 실제 요청에 질문·원문·schema가 함께 들어갈 때의 수용 보장은 아니다. 후속 SDK는 전체 envelope를 먼저 검사하고 초과하면 송신 없이 거부해야 한다. 별도 고정 ‘짧은 질문’ 하한을 숨기거나 예산을 자동 증액하지 않는다.

## 실제 SDK 구성 · 합성 전송

caller-owned `OpenAIResponsesModel(gpt-6.1-sol)`/Responses client를 MockTransport에만 연결했다. reasoning low/default tier·no-store·출력1,800/30초·Agent retry0/transport retry0·요청1회/사용량 한도를 설정했다. 비교 한도 안의10조건은 각1회 합성 HTTP, 초과1조건은0회다. wire의 정확 prompt/지침·strict 단일 도구 이름·정규화 schema와 settings를 대조했다. 네트워크·실제 OpenAI 요청·키 파일 접근은0이다.

응답은 모든 경우 같은 합성 빈 명제/명시 부족 이유다. 설치된 SDK가 도구 형식을 구성하고 이 합성 응답을 읽은 관측일 뿐, 실제 제공자 서버가 이 strict schema를 허용하거나 모델이 의미를 보존/완료한다는 증거는 아니다. 제품 SDK의 독립 영수증·원래 Source/질문 재검증·실패/미완료 usage·추가 도구 거부·취소/앱 전체 예산은 이번 시제품에서 구현하지 않았다.

## 출력 압력

이전의 **기준을 아는 수동**12행/모두uncertain JSON을 질문별 필요 항목으로 나누었다. 자동 추출 결과나 새 정답이 아니며 기존 분모/점수는 변경하지 않는다.

| 수동 예시 | 행 수 | JSON UTF-8 bytes | o200k_base 참고 text tokens |
| --- | ---: | ---: | ---: |
| 질문1 | 4 | 3,769 | 1,331 |
| 질문2 | 3 | 3,102 | 1,035 |
| 질문3 | 2 | 1,347 | 450 |
| 질문4 | 3 | 2,977 | 993 |
| 네 질문의12개 전체 | 12 | 10,916 | 3,746 |

로컬 tiktoken0.14.0은 `gpt-6.1-sol` 매핑을 알지 못해 실제 모델 토큰 수를 인증할 수 없다. 이미 캐시된 o200k_base만 오프라인 참고로 계산했다. cl100k_base는 캐시가 없어 외부 소켓 연결을 거부한 상태에서 사용할 수 없었다. DNS 동작까지 계측한 것은 아니며, 토큰 계산에는 캐시된 인코딩만 사용했다. **참고 text token 수는 실제 모델 usage가 아니며 추론 토큰/도구 framing도 제외한다.** 질문1의 참고1,331이1,800보다 작다는 것만으로 모델이 같은 답을 완료할 여유가 있다고 보장하지 않는다. 참고 인코딩에서 전체12행은1,800을 초과하지만 실제 모델의 정확 초과량으로 확대하지 않는다.

초기 토큰 측정 도우미 이름이 표준 라이브러리를 가려 import 실패/부분 결과를 만들었다. 초기 부분 증거를 보존하고 이름을 고친 뒤 로컬 측정만 다시 실행했다. 실패한 초기 실행을 성공으로 세거나 모의 전송/모델 호출을 다시 실행하지 않았다.

## 다음 구현안

2. 최종 지침/도구/입력 형식·독립 SDK 영수증을 고정하고 전체 envelope 사전 차단을 넣는다. 기존 helper·계약/SDK·과거 응답/usage는 수정하지 않는다. 원문/질문 축약·자동 한도 상승·repair/fallback은 하지 않는다.
3. borrowed Model·정확한 단일 도구·30초/no-store·무재시도와 실패/미완료의 알려진 usage·송신 불확실성을 보존한다. 반환 후 기존 순수 builder/저장 validator로 현재 Source/질문과 다시 대조하며 그 실패에서도 비용을 잃지 않는다.
4. 새 SDK의 실제 schema/settings/mock 전송·경계/오류를 먼저 인수한다. 실제 유료 요청 전에는 질문별 필요한 항목/분모·출력/총예산·실패 기준을 사전 고정한다. 실제 모델의 completion/의미·별도 미관측 자료·앱 합산 예산/권한/복구 인수 전 앱에 연결하지 않는다.

입력 비교의 여유만 보고 실제 SDK·출력 충분성·일반 품질이 완성됐다고 표시하지 않는다. 원래 부분 보존/미표현·P2 이견·실제 비용 TTL 미확인도 그대로 유지한다.


## 독립 검토

연구 증거 검토 C0/I0/M1은 helper normalized 크기와 실제 SDK description 차이를 더 명시할 것을 제안했다. 저장된10개 wire의 tools를 같은 JSON 직렬화 방식으로 비교해8,114bytes를 확인하고45bytes 차이와 raw 여유 내임을 기록했다. 추가 모의/유료 요청은 없다.

수정 범위 재검토 C0/I0/M0을 확인했다. 새 실행 코드는 없으므로 기존8,894QA를 재사용했고 이번 연구를 새 전체QA 성공이나 제품 SDK 구현으로 표시하지 않는다.
